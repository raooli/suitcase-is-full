## 0. 三条结论（先读这个）

1. **Cocos Creator 和 VSCode 不是二选一，是分工。** Cocos 管资源/场景/预制体/构建发布，VSCode 管写代码。本项目还有个特殊性：`assets/core/` 是零 `cc` 依赖的纯 TS，**完全不需要 Cocos 就能开发测试**——这意味着 M1 之前的大量工作可以在 VSCode 里完成，Cocos 只在需要"看见画面"时才打开。
2. **当前仓库还不是 Cocos 工程**，需要先做一次工程合并（M0 的 P0 任务）。这是开工第一个动作，也是最容易踩坑的一步，方案见第 2 节。
3. **美术不阻塞开发，两条线并行。** M1~M3 全部用程序化色块跑通玩法（TDD 13 节 T5 已定），Figma 基准图与批量生产并行推进，接入点在第 M3 之后。把美术当成串行前置是本项目最大的排期浪费。

## 1. 工具分工：Cocos Creator vs VSCode

### 1.1 一句话区分

| | Cocos Creator 3.8.8 | VSCode |
| --- | --- | --- |
| 本质 | 游戏编辑器 + 资源管线 + 构建工具 | 代码编辑器 |
| 不可替代的能力 | 场景/预制体编辑、**图集打包**、资源 `.meta` 管理、**微信小游戏构建与真机预览**、引擎参数配置 | TypeScript 编写/重构/跳转、Vitest 单测、Git 操作 |
| 能不能被对方替代 | ❌ 构建发布只能在这里 | ❌ 写代码的体验它比不了 |

### 1.2 本项目里各管什么

| 工作项 | 在哪里做 | 理由 |
| --- | --- | --- |
| `assets/core/**`（11 个模块，纯逻辑） | **只用 VSCode** | 零 `cc` 依赖，`npm run test` 直接跑；开 Cocos 反而是干扰 |
| `test/**`（Vitest，5 spec / 163 用例） | **只用 VSCode** | 在 `assets/` 之外，不进包 |
| `tools/**`（关卡校验、难度报告） | **只用 VSCode** | Node CLI，与引擎无关 |
| `assets/view/**`（13 个 Cocos 组件） | **代码在 VSCode 写，节点/场景在 Cocos 搭** | 脚本是 TS；挂载、层级、Widget、事件绑定在 Cocos 里做 |
| `assets/scenes/*.scene` | **只在 Cocos 里改** | 手改 `.scene` 是下策 |
| 图集 / 资源导入 / 纹理压缩设置 | **只在 Cocos 里做** | 资源管线的职责 |
| 微信小游戏构建、真机预览 | **只在 Cocos 里做** | 唯一入口 |
| 改代码后的编译检查 | 两者配合 | VSCode 保存 → Cocos 自动重新编译并显示错误 |

### 1.3 推荐工作流（每天怎么配合）

```
1. 打开 Cocos Dashboard → 启动 3.8.8 → 打开本项目
2. Cocos 菜单：开发者 → VS Code 工作流 → 更新 VS Code 智能提示数据（只需做一次）
3. Cocos 菜单：开发者 → VS Code 工作流 → 打开 VS Code（或自己开 VSCode 打开项目根目录）
4. 在 VSCode 写 .ts → 保存 → 切回 Cocos，控制台显示编译结果
5. 在 Cocos 里做场景/预制体/资源 → 切回 VSCode 提交 Git
6. 纯逻辑改动：不开 Cocos，直接 npm run check
```

> 菜单名称以 3.8.8 实际界面为准；若"VS Code 工作流"入口位置不同，在 Cocos 顶部菜单"开发者/Developer"下找 Update VS Code API Data / Add TypeScript Config 同类项。

### 1.4 必须守住的五条（否则会浪费半天排查）

| # | 规则 | 违反后果 |
| --- | --- | --- |
| 1 | **复制 `.ts` 时不要连带复制 `.meta`**；新增脚本的 `.meta` 交给 Cocos 打开工程时自动生成 | UUID 冲突，脚本引用丢失 |
| 2 | **不在 VSCode 里手改 `.scene` / `.prefab` / `.meta`** | 场景损坏且难以回滚 |
| 3 | **清缓存的顺序：改代码 → 校验 + tsc → 最后才清 `temp/` / `library/`** | 先清缓存会导致 tsc 跑不起来，误判为代码问题 |
| 4 | **测试边界：`test/` 只测 `core/`，不测 `view/`** | view 依赖 `cc`，进 Vitest 需要 mock 引擎，收益不抵成本 |
| 5 | **每次提交后追加 `CHANGELOG.md`**（仓库根目录已建） | 见该文件顶部的格式说明 |

## 2. M0 工程落地（开工第一动作）

**问题：** 当前 `assets/` 只是普通目录，没有 `.creator/`、`settings/`、资源 `.meta`，Cocos 不认它。

### 主方案 A：同目录合并（推荐）

单一仓库、单一真相源，`core/` 不需要复制两份。

| 步骤 | 动作 | 验证 |
| --- | --- | --- |
| 1 | Cocos Dashboard → 新建项目 → 空模板（2D）→ 路径选一个**临时空目录**（如 `~/cocos-tmp/suitcase`） | 能正常打开 |
| 2 | 退出编辑器，把临时项目里的 `.creator/`、`settings/`、以及必要的隐藏文件拷入本仓库根目录 | `ls -a` 能看到 `.creator`、`settings` |
| 3 | **tsconfig 冲突处理**（关键）：Cocos 会生成自己的 `tsconfig.json`。把现有根 `tsconfig.json` **改名保留为 `tsconfig.node.json`**，`package.json` 的 `typecheck` 脚本改为 `tsc -p tsconfig.node.json --noEmit`；`vitest.config.ts` 同步指向它 | `npm run check` 仍 163/163 通过 |
| 4 | 核对 `.gitignore`（**已含** `temp/ library/ local/ build/ profiles/ native/ .cocos/`）；只需确认 **`.creator/` 不被忽略**（项目配置要提交）、**`assets/**/*.meta` 不被忽略**（必须提交） | `git check-ignore -v .creator assets/core/config.ts.meta` 无输出 |
| 5 | 用 3.8.8 打开本仓库 → 等待首次资源扫描完成 → **提交新生成的 `assets/**/*.meta`** | `git status` 只多出 `.meta` 文件 |
| 6 | 在 Cocos 里跑一次空场景预览（Web） | 能出画面 |

**回滚：** 步骤 2~4 全部是新增/重命名文件，`git checkout` 即可完整回退；步骤 5 的 `.meta` 提交后不可撤销性低，删掉重开即可重新生成。

### 备选方案 B：Cocos 工程独立目录

另建 `suitcase-cocos/` 工程，`core/` 用同步脚本或 symlink 引入。
**不推荐**：symlink 在 Cocos 资源扫描下行为不确定，且两份代码迟早不同步。仅在方案 A 踩到无法解决的冲突时启用。

#### M1.A 接线契约（view ⇄ core，照表接线，不要自造 API）

**Session API**（`assets/core/session/GameSession.ts`）：

| 方法 | view 何时调 |
| --- | --- |
| `getState(): LevelState` | 每次重绘前读；`placements / tray / trayRotations / selectedId` 是唯一渲染依据 |
| `getPhase(): GamePhase` | `Idle / Selected / Dragging / WinAnimating`——`WinAnimating` 时冻结一切输入 |
| `getPreview(): DragPreview \| null` | **每次 touchmove 后**读，驱动 PreviewLayer；`DragPreview = { itemId, anchor: RC, rotation, check: PlaceCheck, from }` |
| `dispatch(intent): SessionResult` | **唯一的改状态入口**；返回事件数组（见下表），view 据此表现 |
| `completeWinAnimation()` | 通关动画播完后调，解除冻结 |

**Intent 触发时机**（`assets/core/model/types.ts` L142）：

| Intent | 触发 |
| --- | --- |
| `select(itemId \| null)` | 点托盘物品 / 点空白处取消 |
| `grab(itemId, anchor: RC)` | touchstart 且命中物品；anchor = 手指压住的格 |
| `move(anchor: RC)` | touchmove（节流到逐格变化时） |
| `drop` / `cancel` | touchend / touchcancel 或拖出有效区 |
| `rotate(itemId)` | 旋转按钮或双击（原位旋转四策略由 core 处理） |
| `removeToTray(itemId)` | 拖回托盘区松手 |
| `undo` / `reset` | 工具栏（M1 先接 undo，M2 补 reset 的 ConfirmDialog） |

**事件 → 表现**（`assets/core/session/events.ts`，`dispatch()` 返回值是「发生了什么」的唯一来源）：

| 事件 | 表现动作 |
| --- | --- |
| `state-changed` | BoardView + TrayView **整体重绘**（MVP 不做增量 diff） |
| `placement-committed` | 落位动画 / 音效挂点 |
| `placement-rejected` | 回弹动画；`reason` 决定提示文案 |
| `item-rotated` | 按 `placement.rotation` 设置 `Node.angle`（**view 永不自己转 cells**） |
| `rotate-blocked` | 抖动动画（四策略全失败） |
| `item-returned` / `undo-applied` / `level-reset` | 随 `state-changed` 重绘体现 |
| `level-cleared` | 进 `SuccessOverlay`（M1-7） |
| `deadlock-warning` | Toast 挂点（M2-4 实现，M1 仅 Console.warn） |

**两条铁律：** ① view 不直接改任何 core 状态，一切经 `dispatch`；② 渲染只读 `getState()` 快照，事件只用来触发表现（动画/音效），不用来改数据。

#### M1.B 分任务实施要点

- **M1-0**：L1 数据 M1 阶段直接 `parseLevelSpec()` 内联 JSON（真实 `resources.load('data/levels')` 是 M2-1）；`GameController` 命名与文件名严格一致，挂 Game 场景根节点。
- **M1-1**：`rcToPx/pxToRc` **只写在这一个文件**（R-A6，check-arch 会拦）；棋盘锚点取棋盘区域中心，`cellSize = min(可用宽/cols, 可用高/rows)` 向下取整。
- **M1-2**：色块用 `Graphics` 直接画，**本轮不实现 SpriteFrame 加载路径**；着色按 TDD 17.4 明度阶梯（2 格亮、3 格中、4+ 格深，L1 够用即可）。
- **M1-4**：M1-6 未完成前用测试挂具自测——`DragController` 只产出 Intent 打到 Console，人工比对意图序列正确后再接线；`grabOffset` 语义 = 抓取那一刻手指相对物品锚点的偏移，**move 全程保持**（这是 T1/T2 的本质）。
- **M1-6**：`dispatch` 是原子提交——状态变更与事件在同一次调用里返回，view 收到后**一次性**重绘，禁止在单个事件回调里二次改状态。
- **M1-8**（M1-7 复查时补记的任务缺口）：**旋转交互入口**。原任务表只有"旋转"的规则与表现，没有任何一条任务负责"玩家怎么旋转"——结果是 `rotate` intent **没有任何触发路径**，AC06（旋转 4 次回初态）只能在单测里成立，真机上玩家无从旋转。M1 阶段没有工具栏（M2-2 才有旋转按钮），按 M1.A 表的「旋转按钮或双击」取**双击**语义实现：由 `DragController` 报"点到了谁"，`GameController.handleTap` 判——**再次点击已选中的物品 = 旋转**（用"已选中"判定而非双击计时器，避开时间阈值竞态）。同批补 `rotate-blocked` 的抖动反馈（G1-3 要"抖动反馈清晰"）：抖动实现收在 `view/shake.ts`（停 tween 必须归位基准位，M1-5/M1-7 各踩过一次），且该分支**不触发重绘**（状态未变，重绘会把刚要抖的节点重建掉）。注意 **L1/L2 的物品 `rotatable` 全为 false**（教学关设计），旋转只能在 L3+ 端到端验证。
- **每个任务收尾**：`npm run check` 绿 + 手动在 Cocos 预览验证 → 再提交（CHANGELOG 追加一条）。

## 6. 执行纪律

1. **每阶段结束跑一次 `npm run check`**（typecheck + 关卡校验 + 163 单测），不过不进下一阶段。
2. **每次 commit 后追加 `CHANGELOG.md`**（根目录，格式见文件顶部）。
3. **逻辑进 `core/`，表现进 `view/`，平台进 `platform/`** —— 边界一旦破了先修边界再继续，否则成本翻 2～3 倍（TDD 第 2 节）。依赖规则 7 条见 `06-架构设计` 第 1.2 节。
4. **不在没有读数时下性能结论。**
5. **美术锚点未确认，不批量出图。**
