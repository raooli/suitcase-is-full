## 1. 玩法概要与边界

### 1.1 核心目标

玩家将托盘中的**全部必需物品**装入行李箱网格。所有占位格需在边界内、不与障碍格相交、不与其他物品重叠。完成全部摆放后即通关，不要求填满每格；关卡可有多个解。

### 1.2 交互与状态基线（与 PRD 保持一致）

| 主题 | GDD 规则 |
| --- | --- |
| 棋盘坐标 | 左上 `(row=0, col=0)`；行向下，列向右；障碍用坐标数组表达 |
| 形状定义 | 每件物品为 4 邻接连通的相对格坐标 `cells: [[rowOffset,colOffset],...]`，最小偏移归一化为 `(0,0)` |
| 放置 | 从底部托盘拖至棋盘；按固定触点偏移映射到网格；松手后合法则提交，不合法则原子回退 |
| 旋转 | 可旋转物品每次**顺时针 90°**，归一化坐标；不可旋转时按钮禁用 |
| 选中 + 旋转交互 | 点击物品选中，再点击旋转按钮；托盘中旋转先更新其预览朝向（未放置无需写 Undo）；已放置物品原位旋转仅在新朝向合法时提交，否则恢复原朝向，玩家可先移到空处后再转 |
| 拖拽中的旋转 | MVP **不要求**拖拽过程中双指旋转或悬空旋转；避免手势冲突。选中→旋转→拖拽即可完成教学 |
| 已放物品 | 可再次直接拖动；检测碰撞时必须临时忽略自己的旧占位；非法放下（棋盘内但撞格/越界）回到原状态 |
| **取出（V1.1）** | **已放置物品拖到网格范围之外松手 = 取出**：移除占位、回到托盘原 `trayOrder` 位置、**保留取出时朝向**；这是一次成功操作，计入撤回栈。托盘物品拖到网格外松手则无任何变化 |
| **取出 ≠ 取消拖动** | **必须区分**：`touchCancel` / 来电 / 下拉通知等**系统中断**一律恢复操作前状态，**不**视为取出、**不**计入撤回栈 |
| 撤回 | 记录成功提交的：**上箱、箱内移动、合法原位旋转、取出**；托盘的未提交预览旋转不计入；非法尝试不计入 |
| **撤回语义（V1.1）** | **回滚到该操作执行前的完整快照，含位置与朝向**。撤回「取出」→ 回到取出前的位置与朝向；撤回「移动」→ 回原位、朝向不变；撤回「旋转」→ 朝向回到旋转前。**朝向一律不重置为 `cells` 初始朝向** |
| 重置 | 恢复全部物品的 `cells` 初始朝向、初始托盘顺序和空棋盘；仅障碍保留；不影响关卡解锁。（只有重置会回到初始朝向） |
| 通关 | 最后一件**必需**物品合法入箱后触发一次胜利；通关后禁止重复提交输入 |
| **装不下提示（V1.1）** | 每次成功提交后做面积守恒快检：`剩余可用格 < 剩余未放物品格数` → 显示**非阻断**轻提示（约 2 秒自动淡出）。**单向断言**：成立时可说「空间不够」；不成立时**不得**给出任何正向承诺，也不得禁用操作或判失败 |
| 不可解的玩家临时局面 | 不判失败；玩家可移动、取出、撤回或重置；MVP 除上述面积快检外不做实时求解式无解警报 |
| 临时进度 | 不跨进程重启恢复当局布局；只存最高解锁关、已通关集合、静音状态 |

**形状旋转的纯逻辑标准：** 原始格坐标 `(r,c)` 顺时针转一次后先映射为 `(c,-r)`，再整体平移使最小行、列都为 0，最后按行列排序。注意旋转以物品自身形状为原点，而非绕行李箱全局坐标旋转。

**建议输入状态机：** `Idle → Selected → Dragging → Preview → (Commit / Cancel) → Idle`；进入 `WinAnimating` 后冻结物品输入。拖拽与渲染采用同一个逻辑状态源，UI 不直接改占位数组。

### 1.3 视听体验

- **正反馈：** 合法落位给予短弹性回弹（建议 100～180ms）和轻微“啪嗒”音效；不影响快速连续操作。
- **负反馈：** 越界/撞障碍/撞其他物品时出现红色虚线轮廓 + 轻抖（建议 <200ms），自动回到原位；无需弹窗。
- **完成反馈：** 逻辑胜利后盖上行李箱、拉链合拢或扣锁“咔嗒”声，约 0.7～1.2 秒后给出「下一关」。第 10 关为章节完成页。
- **可读性：** 合法/非法状态同时依靠轮廓/图标/文字提示，不仅靠红绿色；设置音效开关。
- **美术优先级：** 占位外形和网格清晰度 > 拖拽手感 > 合箱动画 > 真实物件插画。逻辑形状可能为简化轮廓，贴图必须能让玩家认清占用格。

### 1.4 第一版不做

无计分星级、奖励货币、情节、角色互动、排行榜、限时、操作次数限制、皮肤商城、在线动态关卡、AI 对话、道具扩容与强制广告。激励视频道具可在后续单独评审；本版**没有失败弹窗，也没有广告复活**。

## 2. 关卡结构与渐进教学

### 2.1 难度设计原则

1. 先学触摸落位（1～2 关），再学旋转（第 3 关），再理解密集摆放（4～5 关），随后引入障碍（第 6 关）、长条约束（第 7 关）、分区（第 8 关）和大规模组合（9～10 关）。
2. 一关只强调一个主要新认知，不出现隐藏规则；每关均允许无限次调整和重置。
3. **数学可解性已验证；难度序列已用离线代理指标校准（见 2.4）；主观体感难度仍待试玩。** 若玩家在首测出现长时间卡关，应修改关卡数据而不是直接增加广告道具。**任何关卡数据改动后必须重跑 2.4 的两个指标，确认难度序列仍单调。**
4. 非旋转关的 `rotatable=false` 是教学限制（第 1、2 关）；从第 3 关开始允许旋转，但有些特殊形状的旋转可能不改变外形（如正方形）。
5. 关卡实际展示给玩家的是**空箱 / 障碍 + 待放物品**；下面的字母网格是**设计时的一组标准摆放解**，不是开局已经摆好的界面，更不可在正常游戏中直接显示。

### 2.4 难度校准方法（V1.1 新增）

V1.0 只验证了「数学可解」，没有验证「难度是否递增」。V1.1 引入两个**离线代理指标**做校准。两者都**不是**玩家实测数据，只用于排序和发现异常。

| 指标 | 定义 | 用途 | 局限 |
| --- | --- | --- | --- |
| **big%** | 模拟一个「不假思索」的玩家：按大件优先顺序，每件从所有合法落位里**随机**挑一个放下，一路放到底的成功率（N=3000） | **唯一的难度排序口径**。判定「倒挂」前必须做双比例显著性检验 | 尾段（<1%）命中仅十余次；不能预测真人时长 |
| **解数** | 枚举该关**全部**完整摆放方案的总数（按物品实例区分，确定性、可复现） | **只用于发现结构性异常**（某关解空间比邻关高一个数量级）。**不用于难度排序** | 受节点预算限制时只能给**下界**；受留白格数与物品数强烈影响；**与难度不构成单调关系** |

> **V1.1 修正（推翻 V1.1 初稿的一个结论）：** 初稿把「解数」列为难度排序指标之一，口径是「解越少越难」。TS 工具链跑通后**证伪**了这条：解数与 big% 的排序互相矛盾——L06 只有 18 组解，却比解数 ≥3 万的 L09 更「好放进去」（big% 0.83% vs 0.73%）。原因是两者量的不是同一件事：解数量的是「合法终局有多少个」，而难度取决于「玩家能不能找到其中之一」。**难度排序一律以 big% 为准，解数只用来扫结构性异常。**

**V1.1 校准结果：**

下表 big% 为 Python 工具首轮结果（N=3000）；`解数` 一列受节点预算影响，**带 ≥ 的只是下界**，两套工具的预算不同（Python 约 1e5 节点 / TS 约 2e6 节点），所以同一关的数字可能不同。这不是矛盾，是预算差异。

| 关卡 | 装载格/可用格 | big%（V1.0 → V1.1） | 解数（预算相关） | 说明 |
| --- | ---: | --- | ---: | --- |
| 01 | 9/9 | 66.70% → 66.70% | 8 | 未改动 |
| 02 | 10/12 | 73.43% → 73.43% | 36 | 未改动；与 L01 的 7pp 倒挂在噪声内且两关都极简单，不修 |
| 03 | **16/20** | **2.73% → 59.40%** | 184 | **原为全曲线第二难关，与「旋转教学关」定位严重不符** |

**但「除 L01/L02 外单调递减」这个说法本身站不住，必须收回。** 用 TS 工具复跑（独立实现，结果与 Python 一致到 ±1pp 以内）后加了双比例显著性检验，结论是：

| 相邻对 | 差值 | 2·SE | 判定 |
| --- | ---: | ---: | --- |
| L01→L02 | 5.27% | 2.37% | **真倒挂**（唯一一处） |
| L06→L07 | 0.17% | 0.45% | 不可区分 |
| L07→L08 | 0.27% | 0.38% | 不可区分 |
| L08→L09 | 0.33% | 0.39% | 不可区分 |
| L09→L10 | 0.37% | 0.38% | 不可区分 |

也就是说：**L05～L10 这六关里，除了 L05→L06 之外，相邻两两在本样本量下都无法区分。**「难度单调上升」这个结论目前只有 L02→L05 那一段（含 54 倍量级的大跳变）是真正被数据支持的；尾段只能确认「都在 0.4%~2.8% 这个量级」，具体谁比谁难**必须靠试玩定**。

**对指标的诚实说明（务必连同数字一起读）：**

1. **big% 不能预测真人时长。** 真人会看、会试、会撤回，表现远好于随机玩家。它只对「同一套傻瓜策略下的跨关排序」有意义。
2. **尾段（L07～L10）全部不可区分**，不应认定任何先后顺序。这四关的真实顺序**必须靠试玩定**；在拿到试玩数据之前不要再动这四关的数据。加大 N 也未必有用——0.4% 附近要把 SE 压到 0.1% 以下需要 N≈10 万量级，而「随机放位成功率」这个指标本身在极低区间就已经失真了（真人不会随机放）。**想给尾段排序，正确做法是换指标（例如人类试玩的平均重试次数），而不是加大 N。**
3. **解数一列不要横向比较。** L09 的解数依然远高于其他关（9 件物品 + 1 格留白导致的组合爆炸），L06 则低到只有 18 组。这两个极端都**不**说明难度：解数只用来发现「某关解空间异常宽松」这一件事。

**校准过程中踩到的三个工具陷阱（记录以免重犯）：**

- **蒙特卡洛的随机数发生器必须跨试验连续推进。** 若每次试验都新建 `Random(同一 seed)`，N 次试验会退化成同一次试验重复 N 遍，成功率只会输出 0% 或 100%。本轮校准中途确实出现过这个问题，已修正并与原版基线交叉验证。TS 版工具的实现（`mulberry32`）在循环外建一次 rng，代码里有注释标注。
- **MRV 回溯的首次求解节点数不是可靠的难度指标**，它更多反映「贪心搜索的运气」而非难度（L05 节点数 1160 但 big 仅 0.17%，L08 节点数 4616 但 big 0.53%，两者结论相反）。已弃用。
- **不要把两个代理指标的小数直接比大小。** 0.1%~1% 区间内 N=3000 只有 3~30 次命中，直接比大小会把纯噪声当成「难度倒挂」。**必须先做双比例显著性检验**（`|p1−p2| > 2·SE_diff`），否则会一路追着噪声改关卡数据。本项目的 `tools/difficulty-report.ts` 已内置该检验。

### 2.3 数据图例与旋转规则

- 网格中的 `A`～`I`：不同物品的 **实例编号后缀**，如 `L03_D` 对应字母 `D`。
- `#`：固定障碍格，玩家不能放入物品。
- `.`：标准解中的**未使用合法空格**，不是障碍，可以被摆放；只是该组标准解没有用到。
- **坐标为 0 起点**；物品 `cells` 已归一化。`标准解 (r,c,转数)` 中的 `(r,c)` 是旋转后形状的左上锚点，`转数=1` 表示顺时针转 90°，`2` 表示 180°，`3` 表示 270°。
- `初始形状` 是**开局托盘里的逻辑形状**；不是字母解图上该物品的朝向。请严格以 JSON 中 `cells` 为准。
- `默认顺序` 按 JSON `trayOrder` 从小到大；所有物品都是必需的，默认初始状态均未放入行李箱。
- 这些标准解用于求解器回归测试、调试和编辑器预览；**不得作为游戏开局状态**。

## 4. 数据契约：与技术实现对接

### 4.1 配置组织形式

配套 JSON 的根对象：

```ts
interface LevelPack {
  schemaVersion: "1.1";
  gameId: "suitcase-packing";
  levels: LevelData[];
}

type RC = [row: number, col: number];

interface LevelData {
  levelId: number;                 // 1..10，连续且唯一
  title: string;
  board: { rows: number; cols: number; blockedCells: RC[] };
  items: Array<{
    id: string;                    // 关卡内唯一实例 ID，例如 L03_D
    itemType: string;              // 后续主题复用 / 素材映射键
    name: string;
    spriteKey: string;             // 第一版 placeholder 占位资源键
    cells: RC[];                   // 已排序、归一化，4 连通
    rotatable: boolean;
    initialRotation: 0;            // cells 已表达开局朝向，勿再次旋转
    trayOrder: number;              // 从 1 开始；所有 items 均为必需
  }>;
  solution: Array<{
    itemId: string;
    row: number;
    col: number;
    rotation: 0 | 1 | 2 | 3;       // 顺时针旋转次数
  }>;
  solutionGrid: string[];          // 仅编辑器 / 单元测试用
  verification: {
    solvable: boolean;
    solutionsFound: number;        // 搜索计数，可能被截断
    solutionCountCapped: boolean;   // true 时不代表确切解数
    solvableWithoutRotation: boolean;
    occupiedCells: number;
    blockedCells: number;
    emptyCells: number;
  };
}
```

所有格子坐标在 JSON 中统一序列化为 `[row, col]` 二元数组。技术设计阶段可将 `solution`、`solutionGrid`、`verification` 作为**开发专用字段**剥离，生产构建仅保留核心棋盘与物品数据。

### 4.2 生产态与开发态的边界

- **开发态：** 保留标准解、求解验证、调试可视化，以及校验报告；任何修改关卡 JSON 必须重新运行校验。
- **生产态：** 只载入关卡规则与可见信息；不要把解图直接渲染到正常玩家屏幕。
- **渲染层：** `spriteKey` 目前是占位资源路径（如 `placeholder/03/A`），并非已经制作好的 PNG。可用规则化彩色形状先跑通玩法，不能假定这些资源已存在。
- **离线求解器：** 开发/CI 时执行，**不用每次启动小游戏都全量求解全部关卡**。
- **提示道具（未来 P1）：** 可以保存部分标准解做静态参考，但玩家改变布局后，不能把静态答案直接当作可执行安全提示；需对当前占用状态重新求解，或引导撤回。

### 4.3 合法性判定伪代码

```ts
function canPlace(item, anchorRow, anchorCol, rotation, board, placedItems) {
  const rotatedCells = normalize(rotateQuarterTurns(item.cells, rotation));
  return rotatedCells.every(([dr, dc]) => {
    const r = anchorRow + dr;
    const c = anchorCol + dc;
    return inBounds(board, r, c)
      && !isBlocked(board, r, c)
      && !occupiedByAnotherItem(placedItems, item.id, r, c);
  });
}
```

提交放置需要使用一个统一的 `Move` 操作对象；仅在 `canPlace` 为真时修改状态并追加撤回历史。拖动/放置动画只能读取提交后的状态，不得独立维护占位真相。

## 5. 关卡可解性与质量校验

### 5.1 已执行的自动化校验

在生成本 GDD 时，使用独立 Python 3 校验脚本执行：

1. 棋盘尺寸、障碍格不重复且不越界；物品实例 ID 唯一、托盘序号连续。
2. 每件物品占位坐标为整数、无重复、归一化、4 邻接连通。
3. `solution` 对每件必需物品恰好出现一次；每个旋转与左上角锚点均能合法落位。
4. 标准解无重叠/越界/覆盖障碍，与逐字符 `solutionGrid` 完全一致。
5. 使用独立的回溯求解器至少找到一组合法完整摆放，不仅依赖人工附带的标准解。
6. **第 3 关附加校验：** 禁止所有旋转时求解器无解，开放旋转时有解。

**校验结果（V1.1 数据）：10/10 关通过，标准解全部合法；第 3 关旋转约束通过。** 这是对当前配套 JSON 的静态验证结果，不是玩家难度测试或商业化结果。难度序列另见 2.4 的代理指标。**注意：V1.1 的数据改动已使标准解与解图重新生成，V1.0 的旧标准解不再有效。**

运行方法（把三个文件放在同一目录）：

```bash
python 02-GDD-validator-v1.0.py
# 或指定关卡数据路径
python 02-GDD-validator-v1.0.py ./02-GDD-levels-v1.0.json
```

**V1.1 之后的工具链（TS 版，已落地在仓库里）：**

```bash
npm run verify:levels        # 结构 + 标准解 + 独立求解 + L03 旋转断言 → 生成生产态 assets/data/levels.json
npm run report:difficulty    # big% / 解数 / 显著性检验
npm run check                # 类型检查 + 上面两项 + 单测
```

两者是**互相独立**的实现（Python 手写校验器 / TS 复用 `assets/core`），跑出来结论一致（big% 逐关相差 ≤1pp），这是本轮校准可信度最高的证据。按 TDD 9.2 的安排：TS 版稳定后，Python 版降为**历史快照**，不再承担结论产出——两套逻辑漂移只是时间问题。

### 5.2 仍需人工试玩验证的问题

- 1～3 关是否不看讲解也会玩；第 3 关旋转引导是否一看就懂。
- 第 4～10 关是否出现超时长的挫败或过度轻松；**有多组数学解不等于玩家觉得容易**。
- 细长物品是否因手指遮挡而难以对齐；6×6 棋盘在小屏手机上的触摸精度是否足够。
- 物品插画和逻辑网格形状是否一致，是否产生“明明没碰到却判定冲突”的观感。
- 无限重排是否足以支撑持续玩下去；是否有必要在后续版本加入轻量目标或挑战变体。

### 5.3 调整关卡的规则

- 修改任何一个 `cells`、`rotatable`、障碍坐标或标准解时，**先重新跑校验器，再重跑 2.4 的难度代理指标**；禁止只编辑标准解图示但忘记同步机器数据。**只保证「有解」是不够的——V1.0 的 10 关全部有解，难度序列却是错乱的。**
- 调整每一关难度优先顺序：物品数量 → 棋盘空余格 → 不规则形状比例 → 障碍布局 → 可旋转限制；避免以误导玩家、突然加倒计时等方式做难度。
- 小规模首测至少记录各关：进入次数、完成次数、完成用时、中途退出、重置次数、非法落位次数、操作反馈问题；样本少时只作为定性修正依据。

## 7. 迭代策略、依赖与交付

**开发顺序（建议）：**

1. **机制样机：** 第 1、3 关 + 纯几何物品形状，验收拖拽、选中旋转、回退与通关。
2. **体验样机：** 第 4、6、8 关，验收完全填满、障碍和左右分区的显示与求解。
3. **MVP：** 载入全部 10 关、撤回/重置/关卡列表/本地进度/音效/章节完成页。
4. **试玩校准：** 记录实际用时与卡点后形成 `GDD v1.1`，只在明确观察到问题时改变规则。
5. **商业化评估：** 如玩家确实需要帮助，可独立提出「智能提示 + 自愿激励广告」方案；该模块属于 P1，绝不通过制造无解关卡驱动广告。

**与后续文档分工：** GDD 负责规则、关卡数据、标准解和玩家体验；`03-UI-Spec.md` 负责界面布局、配色、资源规格与动效；`04-TDD.md` 负责 Cocos Creator 工程版本、触控锚点算法、状态管理、求解复杂度、撤回实现和自动化测试；不要在 GDD 中硬编码引擎 API。
