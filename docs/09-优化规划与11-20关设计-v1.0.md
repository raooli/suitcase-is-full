## 3. 底部托盘：直接看懂物品占格形状

### 3.1 用户问题与代码依据

玩家需要在底部判断「这件物品要匹配什么形状的空位」，目前插画无法稳定表达逻辑格子，选中也不能解决这个问题。

- `assets/view/ItemView.ts` 的 `setSpriteFrame()` 在真图就绪后关闭原有 `Graphics`。插画取代了程序化格形显示，格子边界和凹口未作为独立信息持续保留。
- `assets/view/TraySlot.ts` 的 `redraw()` 在选中时改变整张卡片的边框颜色与线宽，没有突出物品自身的占格轮廓。
- `assets/view/TrayView.ts` 的 `slotSizeFor()` 按件数均分槽位并夹在 44–76 设计单位之间。后期物品较多时，点击区域即使可用，形状细节仍可能过小。
- 托盘已使用 `trayRotationOf()`、`rotateBy()` 和 `source.shapeMetrics()`，可以复用当前朝向与形状数据，不需要增加另一套玩法判定。

**本项目标：未选中时即可看懂实际形状；选中后更清楚；旋转、撤回、取出后始终与棋盘判定一致。**

### 3.2 展示方案

采用「格形为主体、物品身份为辅助」的托盘卡片：

1. **真实占格示意常驻。** 按当前旋转后的 `cells` 绘制每一个占用格，保留内部格线与外轮廓。不要用完整包围盒代替真实形状。
2. **凹口和空洞清楚。** 不占用的格子保持留白，与占用格形成明确区别；L、T、Z 等形状不能被填成矩形。
3. **插画与形状分区呈现。** 卡片主体展示格形，插画放在独立角标或辅助区域；空间不足时优先保证格形，选中信息区再展示名称和插画。插画不得遮住关键格线和凹口。
4. **选中强化物品轮廓。** 卡片边框之外，同时强化真实格形描边，并显示「物品名 · 占 N 格 · 可旋转/固定朝向」。占格数取 `cells.length`，不能用包围盒面积代替。
5. **朝向实时一致。** 点击旋转后，格形立即顺时针旋转 90°；撤回恢复相应朝向；从棋盘取回时保留当时朝向。
6. **数量多时优先滚动。** 槽位尺寸优先保证形状可读性，减少对件数均分缩小的依赖；通过横向滚动及轻量方向提示访问其余物品。
7. **不增加操作门槛。** 看形状不需要长按、拖起或打开弹窗。原有点击、拖拽、横向滑动的操作方式保持连贯。

格形示意（仅用于解释逻辑；`■` 为占用格，`·` 为不占用格）：

```text
横条：占 3 格     L 形：占 4 格     T 形：占 4 格
■ ■ ■           ■ · ·           ■ ■ ■
                ■ ■ ■           · ■ ·
```

「3×2 包围盒」不能代替「L 形占 4 格」的表达。实际 UI 中不占用位置应明显留白，避免把示意背景误读为物品占格。

### 3.3 状态与反馈

| 状态 | 底部显示 | 一致性要求 |
| --- | --- | --- |
| 未选中 | 完整格形、当前朝向、辅助插画 | 不依赖选中即可辨认 |
| 已选中 | 加强格形轮廓，显示占格数与旋转状态 | 选中不改变形状、位置或朝向 |
| 旋转后 | 格形与插画方向同步更新 | 与 core 的旋转结果一致；连续四次回到初始朝向 |
| 提示中 | 对应物品滚入可见区，显示提示标识；目标朝向另作明确示意 | 当前朝向与建议朝向可区分，不偷偷改变物品状态 |
| 拖拽中 | 延续现有托盘隐藏及 ghost 机制 | 起拖时不跳格，不因装饰层改变抓取偏移 |
| 取出或撤回后 | 物品回托盘时重新显示对应形状与朝向 | 与已提交状态、历史快照一致 |
| 插画未加载或加载失败 | 格形照常可见 | 占格信息不依赖贴图加载成功 |

### 3.4 技术实现边界

- 形状真相源：`ItemSpec.cells` 与 `trayRotationOf(state, item.id)`；使用 `rotateBy()` 获得当前格形。
- 继续由 `BoardView.shapeMetrics()` 提供格子到像素的指标，托盘只对整体结果缩放。不要在 `TraySlot` 再建立独立的网格换算。
- 托盘格形与插画使用独立渲染节点。真图加载成功只更新插画层，不应再关闭托盘的形状层。
- 需要区分托盘展示模式与棋盘展示模式，避免改动共享 `ItemView` 后意外改变已放物品的表现。
- 卡片上插画角标、名称和图标均为装饰，不注册新的触摸监听；手势继续由 `DragController` 统一处理。
- 如果拆分格形与插画节点，`TraySlot.getItemNode()` / `TrayView.hitTest()` 返回的抓取参考节点应指向实际格形的坐标系，不能改成插画角标或卡片整体，否则会改变 `grabOffset`。
- 视觉参数集中管理。点击热区按设备逻辑像素验证不低于现有 44px 目标，不能直接把设计单位或截图物理像素当作同一量纲。
- 可读性先以缩略图单格不小于约 8 个设备逻辑像素作为原型目标，再通过真机与试玩定稿；不足时调整卡片尺寸或滚动容量。

### 3.5 验收标准

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |

| TRAY-02 | L/T/Z、长条、矩形等代表物品 | 渲染占格集合与旋转后的 `cells` 一致，不用实心包围盒替代 |

## 4. 已确认技术问题的修复目标

### 4.1 安全提示

现有 `suggestNextPlacement()` 按托盘顺序寻找首个合法落点，没有验证剩余物品是否仍可装下。

本轮复现：

- 第 8 关初始局面有解；第一次提示 `L08_A@(0,0), rotation=0`，固定此物品后剩余拼装无解。
- 第 10 关初始局面有解；第一次提示同样推荐 `L10_A@(0,0), rotation=0`，固定此物品后剩余拼装无解。
- 第 4、6 关连续采用提示至第 2 步，第 7 关至第 3 步，第 5 关至第 4 步，第 9 关至第 5 步，也出现破坏剩余可解性的情况。

这里的「无解」指保持当前已放物品不动时没有续解；游戏仍允许移动、取出和撤回，并非永久卡死。

实现要求：

1. 区分「存在合法落点」与「存在安全续解」；前者可以用于即时可放性判断，后者才用于帮助玩家完成关卡。
2. 提示搜索固定当前已放物品，寻找其余物品的完整解，再取其中一步展示。
3. 已有布局无续解时，给出经过验证的调整或撤回建议；不能随意声称撤回一步就一定可解。
4. 保留 `solved / unsolvable / unknown` 区分；达到计算预算只能报告未确定。
5. 搜索按需触发，设置预算、取消和过期结果保护，避免每次拖动都同步执行完整求解。
6. 回归覆盖反例、所有 20 关连续提示、可解中间局面、无续解局面与超预算结果。

### 5.1 新机制的明确规则

「指定分区收纳」仅增加一类放置约束：

- 带分区标记的物品，旋转后的全部占格必须落在对应区域内。
- 未标记物品沿用原放置规则，可以使用任意合法空格，包括标记区域。这让「为受限物品预留空间」成为明确策略。
- 区域边界不限制拖动路径，不引入滑块移动或通道通行规则。
- 区域与物品使用相同图标，并配文字说明；选中物品时突出允许区域，不能只使用颜色表达。
- 落在错误区域时给出明确原因并回退，不改变已提交状态。
- 教学明确「标记约束物品」的语义，避免玩家将区域误解为禁止所有其他物品进入的专属区。

### 5.2 每关的制作交付物

每关交付：关卡 ID 与标题、机制目标、棋盘与障碍、物品清单、形状与旋转限制、必要的分区约束、至少一组合法标准解、教学配置、人工试玩记录及最终排序依据。

先确定解和内容目标，再构造并验证关卡；使用离线工具检查结构、标准解和独立可解性。需要证明的机制目标单独验证，例如「必须旋转」「确实使用分区约束」。不能仅用面积足够、存在解或求解节点数断言真实难度。

关卡节奏允许缓冲。11、16、19 关降低压力，15、20 关形成阶段性挑战；最终顺序由实际试玩校准。

## 6. 架构与工程实施目标

### 6.1 模块边界

| 模块 | 本轮目标 |
| --- | --- |
| 关卡目录与数据 | 增加章节、教学与内容版本信息；编号连续、唯一，原关卡保持兼容 |
| 放置规则 | 分区约束进入统一纯逻辑判定；明确新增非法原因 |
| 求解器与提示 | 候选生成遵循同一分区约束，支持保留已放物品的续解；保留 `unknown` 语义 |
| 托盘视图 | 独立形状展示层，形状与插画分区；复用既有坐标转换与手势入口 |
| 进度协调 | 内容更新后归一化解锁，维护旧档兼容与章节完成行为 |
| 统计接口 | 订阅已提交事实与场景生命周期，不把上传或平台 SDK 放进 core |
| 游戏控制器 | 随功能实现拆出提示、进度协调、统计等职责，保留统一装配和状态流 |
| 资源管理 | 复用形状匹配的现有素材，检查跨关复用的一致性，测量包体与连续游玩内存 |

现有 schema 只描述障碍、物品格形和旋转能力。分区机制须同步更新 schema 校验、运行时判定、solver 候选生成、提示、预览和教学；仅绘制分区边框无法实现约束。

### 6.2 工程风险与约束

- **空洞剪枝：** `ENABLE_HOLE_PRUNE` 当前关闭。现有判据把小于剩余最小物品的空区判死，没有考虑允许留空；不能直接开启作为扩关性能优化。最小反例为 1×4 棋盘、障碍 `(0,1)`、一件横向二连块，其合法解在 `(0,2)`，启用现有剪枝后会误判。修改时需要满填与非满填对照测试。
- **手势所有权：** 当前没有按 touch ID 认领和隔离手势，第二根手指可能重置进行中的拖拽。属于静态检查识别的风险，需通过多指及前后台切换用例验证。
- **渲染优化：** 当前物品层在提交变更后全量重建，并非每个触摸帧都重建。先测量性能，仅在有数据支持时引入节点复用或局部更新。
- **资源复用：** 相同 `itemType` 应保持一致的格形与资源契约。现有美术检查聚合相同 `itemType` 时没有完整比对后续出现的形状，扩关应补一致性检查。
- **资源预算：** 历史构建包体不能代表增加新素材后的体积。新内容完成后重新测量包体、冷启动与连续 20 关内存；资源缓存没有主动释放策略时尤其需要记录峰值。
- **工具链与 CI：** 固定预览所需 Node 版本。CI 分开处理纯 TS 检查和依赖 Cocos 声明/构建环境的检查，不依赖开发者机器上偶然存在的 `temp/` 文件。
- **文档同步：** 实施时同步 PRD、GDD、UI Spec、TDD、实施计划及相关测试，清理当前行为与历史说明不一致的内容；本文作为新一轮执行入口。

## 8. 总体验收与试玩指标

### 8.1 功能验收

- [ ] 底部每件物品直接可辨真实占格形状，选中、旋转、拖拽、取出与撤回一致。
- [ ] 前 10 关玩法与进度无回归，所有 20 关可载入并有独立验证的合法解。
- [ ] 从初始局面连续采用安全提示可完成 20 关；无续解和未确定结果分别处理。
- [ ] 新旧存档、全通与部分通关、静音及已学引导通过兼容验证。
- [ ] 1–20 关全部入口可访问，锁定、已完成和当前关状态正确。
- [ ] 分区预览、实际放置、旋转、撤回、solver 与提示遵守相同约束。
- [ ] 第 10 关到第二章衔接正确；第 20 关不出现不存在的下一关。
- [ ] 普通屏、短屏、安全区和两种启动入口完成视觉与操作验证。
- [ ] 多指、切后台、快速旋转/拖放/撤回/重置后，无残留 ghost、错放和状态分叉。
- [ ] 完成目标微信设备的音频与性能测试，记录包体、内存和帧率；沿用项目中低端机 ≥50fps 的内部目标并给出实测口径。

### 8.2 试玩观察

先接入本地事件记录与导出：`level_start`、`level_complete`、`level_exit`、`item_place_invalid`、`item_rotate`、`hint_requested`、`hint_result`、`undo_used`、`level_restart`。字段包括关卡 ID、内容版本、结果原因、操作计数与有效游玩时长，不记录不必要的身份信息。

有效时长应排除后台停留，并区分首次与重玩。观察每关完成情况、用时、非法落位频次、提示需求和退出位置；对托盘额外记录形状辨识错误、旋转理解错误及滚动发现问题。

5–8 人样本用于发现可用性和卡点问题，不足以证明市场需求或可靠留存。玩法数据用于调整关卡与表现，正式线上统计按后续需要接入。
