## 1. 项目背景与产品目标

### 1.1 背景

开发者具有 React / TypeScript 前端开发经验，计划使用 AI 编程工具个人开发小游戏，以可控的时间和成本验证玩法吸引力、玩家反馈与后续商业化可能性。产品首选微信小游戏，保留跨平台迁移空间。

现阶段不追求“大而全”或完整商业化，而是先完成一个具有完整核心循环、能交给真实玩家试玩的 MVP。

### 1.2 产品目标（按优先级）

1. **可玩：** 10 个经验证可解的关卡，玩家可从开始到通关、自动进入下一关。
2. **好操作：** 拖拽、旋转、网格吸附和反馈清晰；竖屏单手操作没有明显阻碍。
3. **有爽感：** 合法摆放和最终关箱具有即时、舒适的视听反馈。
4. **可扩展：** 后续增加“化妆包、衣柜、冰箱”等主题时，尽量复用摆放规则及数据结构。
5. **可验证：** 能收集不含个人身份信息的基础玩法指标；关卡必须有自动化可解性校验。

### 1.3 第一版成功判据

- **功能性硬门槛：** P0 功能全部通过验收；10 关均有可复现的标准解；没有已知阻断性崩溃、丢进度或非法叠放问题。
- **体验性验证（目标值，非行业事实）：** 邀请至少 5 名未参与开发的试玩者；多数人无需口头指导即可完成前 2 关；记录前 3 关完成率、卡点与操作反馈。样本量很小，只用于发现问题，**不以此声称市场需求已得到证明**。
- **商业化判断：** MVP 仅确认可预留激励广告触发位；不设置收入 KPI，不以“看广告复活”作为核心设计依据。

### 1.4 非目标（明确不做）

第一版**不做**人物剧情、乙游角色、Live2D、在线 AI、用户账号/后端服务、联网排行榜、社交分享裂变、签到/每日任务、在线商城、复杂养成、运营后台、实时随机生成关卡、限时倒计时、步数生命值、强制插屏广告、付费道具。

## 2. 目标用户与体验主张

### 2.1 目标用户假设

- 喜欢整理收纳、空间拼图与轻度解谜的休闲玩家。
- 倾向利用碎片时间体验 30 秒～3 分钟的单局游戏。
- 喜欢视觉秩序恢复、清晰反馈、反复尝试解决难题的玩家。

以上是**产品假设**，不是已验证的人群画像；后续以实际试玩与数据修正。产品可以采用偏清新、精致生活的视觉表达，但不把任何性别作为进入门槛。

### 2.2 三项核心体验

| 体验 | 机制来源 | 设计要求 |
| --- | --- | --- |
| 解压感 | 散乱物品被整齐收纳 | 拖放顺畅、落位动画短、音效柔和；不强制倒计时 |
| “差一点” | 有空间却不一定容得下指定形状 | 可随时拿起已放物品调整；错误有反馈但无惩罚 |
| 成就感 | 找到符合所有约束的摆放组合 | 通关时行李箱合拢、出现明确的下一关入口 |

### 2.3 主玩法与主题边界

- **玩法内核：** 规则化二维多格形状装箱（polyomino packing）。
- **主题包装：** 行李箱、旅行用品、周末出游；物品插画映射到逻辑网格形状。
- **扩展原则：** 主题不能改变底层合法性判定；新增玩法规则需通过配置或独立规则模块接入。

## 3. 游戏核心循环

```text
打开游戏 / 继续游戏
    ↓
进入当前关卡（行李箱 + 待装物品）
    ↓
选择物品 → 拖动 → 预览位置 → 松手放置
                     ↘ 可选：90°旋转
    ↓
合法落位？ ── 否 → 返回拖动前状态 / 物品托盘
    │ 是
    ↓
物品占用网格；剩余物品减少
    ↓
全部必需物品已合法放置？ ── 否 → 继续调整 / 撤回 / 重置
    │ 是
    ↓
通关动画 → 记录进度 → 下一关
```

**MVP 约定：** 不存在耗尽生命、倒计时结束或槽位爆满等失败条件；玩家可以一直调整布局直到成功，也可以主动重置。广告复活不在第一版范围内。

## 4. 基础规则（开发实现必须遵循）

### 4.1 棋盘

- 行李箱内部抽象为 `rows × cols` 的矩形离散网格；设计上支持不同尺寸的关卡。
- 左上角为坐标原点 `(row=0, col=0)`，行号向下递增、列号向右递增。
- 单格只有三种状态：`空闲`、`障碍`、`被某个物品占用`。
- 障碍格既不可摆放也不可移动；MVP 可通过关卡配置预先指定。
- 棋盘视觉可以是旅行箱插画，但逻辑格子大小应一致；不得因美术外形影响碰撞结果。

### 4.2 物品

- 每个物品具有**关卡内唯一实例 ID**、展示名称、外观资源键与占位格集合。
- 逻辑形状由相对于自身左上锚点的整数格坐标表达，例如 `[[0,0],[1,0],[1,1]]`。
- 物品的占位格必须连续连通；不允许空形状、重复格坐标或超出配置上限的异常形状。
- MVP 支持 1 格及多格物品、L / T / 条形等不规则形状；具体物品与格子形状由 GDD 定义。
- 物品只占一层，不存在重叠堆叠或物品厚度概念。
- 物品可配置是否允许旋转。允许时，每次顺时针旋转 `90°`；旋转后归一化坐标，使最小行列均为 0。
- 视觉图片的透明区、阴影等不参与碰撞；**逻辑占位以格子为唯一依据**。

### 4.3 拖拽与落位

**R-01 从托盘拖入：** 按住下方未放置物品即可拖动。拖动过程中，物品随指针/手指移动，并在棋盘内实时显示候选网格位置。

**R-02 选点与吸附：** 使用稳定的拖动锚点计算候选放置位置，松开时吸附至最近的网格锚点；避免由于触点在物品不同位置导致“跳格”。具体触点偏移算法在 TDD 中定义。

**R-03 合法判定：** 某次落位仅在以下条件全部满足时合法：

1. 物品旋转后的每个占位格均在棋盘边界内；
2. 没有占用障碍格；
3. 没有与其他已放置物品的格子重叠。

**R-04 实时预览：** 合法时显示绿色/正向反馈，非法时显示红色/警示反馈；同时通过位置、轮廓或图标传达状态，不仅依靠颜色（便于色觉差异用户识别）。

**R-05 松手处理：** 松手位置按下表判定，三种结果互斥：

| 松手位置 | 物品来源 | 结果 | 是否进入撤回栈 |
| --- | --- | --- | --- |
| 棋盘内且合法 | 托盘或箱内 | 落位并播放短反馈 | **是** |
| 棋盘内但非法 | 托盘 | 取消，返回托盘 | 否 |
| 棋盘内但非法 | 箱内 | 取消，回到操作前位置与朝向 | 否 |
| **棋盘网格之外** | **箱内（已放置）** | **取出，回到托盘（见 R-06b）** | **是** |
| 棋盘网格之外 | 托盘（从未入箱） | 无操作，留在托盘 | 否 |

**R-06 已放物品再调整：** 玩家可以直接拖动已放置物品，不需额外操作。拖动期间应临时忽略其自己的原占位格；只有合法松手才提交新布局。

**R-06b 取出（V1.1 新增）：** 把**已放置**物品拖到行李箱网格范围之外松手，视为「取出」：

1. 该物品从棋盘移除，释放其占用的全部格子；
2. 物品回到托盘中它原本的 `trayOrder` 位置（不是追加到末尾）；
3. **保留取出时的朝向**，不重置为初始朝向（与 R-09 撤回语义一致）；
4. 取出是一次成功操作，进入撤回栈，可单独撤回；撤回后回到取出前的位置与朝向；
5. 取出后重新计算 R-10「装不下」提示（空格变多，提示应消失）。

**判定口径：** 「网格之外」以棋盘包围盒为准，向外扩半格后仍不在其中即算外部；托盘区域、页面空白、顶部区域均属于外部。**必须区分「主动拖到外部松手」与「拖拽被系统中断」**——`touchCancel` / 来电 / 下拉通知等中断**不算取出**，一律恢复操作前状态，且不计入撤回栈。

**预览表现：** 拖到网格之外时，预览应显示为「取出」状态（物品半透明 + 托盘目标位高亮），**不能**显示为红色非法——否则玩家会以为操作失败而不敢松手。

> **为什么必须有这条：** V1.0 中「已放物品拖出箱外 = 回原位」与 R-06 组合后，玩家**没有任何办法把物品从箱里取回托盘**，只能连续点撤回或整关重置。而难度实测显示中后期关卡「一次不回头放完」的成功率不足 1%，卡住是常态。这与本文档 2.2 声明的「可随时拿起已放物品调整、错误有反馈但无惩罚」直接冲突。

**R-07 放置一致性：** 单次拖动/放下视为原子操作，不允许出现视觉已落位、逻辑却未更新或相反情况。

### 4.4 旋转操作

- MVP 使用明确可点击的 **“旋转 90°”按钮**，不依赖多指手势。
- 拖拽结束后的选中物品或拖动中的物品可以旋转；若实现双状态增加风险，**最小实现优先支持“点击选中物品 → 旋转 → 拖动落位”**，并在试玩中验证是否顺手。
- 旋转后立即刷新轮廓和合法性预览；若旋转后的**已放置物品**在原锚点位置发生冲突，则不提交非法占位：可保持待放置预览，并要求重新选择合法位置，或取消并恢复原朝向（具体表现需在 UI/TDD 中统一，验收以“不会生成非法棋盘状态”为硬要求）。
- 不能旋转的物品，旋转按钮应禁用或不给予该操作。

### 4.5 操作与撤回

- **R-08 撤回（Undo）：** 撤回最近一次**成功提交的**操作，包括：放置、箱内移动、合法的原位旋转、**取出（R-06b）**。无历史时按钮置灰。非法尝试不进入撤回栈。
- **R-09 撤回的语义：** 撤回是**回滚到该操作执行前的完整快照**，包含位置**与朝向**。

  | 被撤回的操作 | 撤回后的结果 |
  | --- | --- |
  | 从托盘放入 | 物品回到托盘，朝向 = 放入时的朝向 |
  | 箱内移动 | 回到移动前的位置，朝向不变 |
  | 合法的原位旋转 | 朝向回到旋转前，位置不变 |
  | **取出** | **回到棋盘原位，朝向 = 取出时的朝向** |

  **朝向不因撤回而重置为 `cells` 初始朝向。** 玩家连续旋转 3 次才把一件物品放进箱子，撤回后若发现朝向被重置，会直接判定为 bug。

- **重置（Restart）：** 弹出轻确认（防误触），清空本关所有摆放状态，恢复物品的配置初始状态（初始朝向、初始托盘顺序、空棋盘）；不影响已经解锁的关卡。
- **取消拖动：** 非法松手、或拖动被系统中断时，恢复上一个有效状态，不计为一次成功移动。**注意：** 主动拖到网格之外松手已由 R-06b 定义为「取出」，不属于取消拖动。
- **暂停/退出：** MVP 优先保证“已完成关卡进度”保存；**关卡中的临时布局默认不跨重启恢复**，避免在小版本内引入存档兼容复杂性。退出再进可从该关初始布局开始。
- **关卡切换：** 通关后才解锁下一关；已有通关关卡可重玩，但不回退最高解锁进度。

### 4.6 通关条件

- 该关全部**必需物品**均处于棋盘内且合法放置，即通关。
- **不要求填满每一个空格**；`物品总面积 = 可用格面积` 并非默认要求。
- 关卡只有一个必需物品集合；选装物品、星级奖励、分数/计时排行均不属于 MVP。
- 当最后一件物品合法落位时，先完成逻辑检查再触发通关动画和存档；通关事件必须只触发一次。
- 第 10 关完成后展示“已完成当前章节 / 敬请期待”的终点页，不跳转到不存在的第 11 关。

### 4.7 不适用的机制

第一版**没有**步数上限、倒计时、生命值、失败弹窗、强制广告复活，也没有道具奖励导致的棋盘结构变化。任何后续商业化功能不得暗中修改既有关卡的可解性。

### 4.8 「装不下」面积守恒提示（V1.1 新增）

**R-10 面积快检：** 每次成功提交（放置 / 移动 / 取出 / 撤回 / 重置）之后，计算一次：

```text
剩余可用空格数 = 棋盘总格数 - 障碍格数 - 当前已占用格数
剩余待放总格数 = Σ(未放置物品的格数)
若 剩余可用空格数 < 剩余待放总格数 → 显示提示
```

**表现约束：**

1. **非阻断**：一句轻提示条（例如「剩余空间不够啦，试着挪一挪？」）配一个图标，约 2 秒后自动淡出；不弹窗、不遮挡棋盘、不禁用任何输入、不暂停计时（本就没有计时）。
2. **不判失败**：触发提示时玩家仍可继续拖动、取出、撤回、重置。本关**没有失败状态**，提示只是信息。
3. **文案必须是「空间不够」而不是「你输了 / 无解」**。

**逻辑边界（必须写进实现）：** 该条件是**充分不必要**的——

- 「剩余空格 < 剩余物品格数」成立 ⇒ 一定装不下（可以下这个结论）；
- 不成立 ⇒ **不能**推出装得下（剩余空间可能碎片化，形状放不进去）。

因此实现上**只做单向断言**：条件成立时提示，条件不成立时**什么都不做**，绝不能反向给出「空间充足」的正向承诺，更不能据此禁用操作或判定通关。

**成本：** 每次提交 O(格数)，最大 6×6 = 36 格，可忽略。这是 MVP 唯一做的"提示"能力；完整的求解式提示（F15）仍属 P1，不要在 MVP 里顺手实现。

### 6.3 UI/交互约束

- 支持主流手机竖屏长宽比，适配安全区、刘海屏及底部手势区域；不得把关键按钮放在不可触达位置。
- 棋盘必须视觉显著；托盘与棋盘有清晰空间分隔。
- 拖拽物品应显示适当偏移，避免手指完全遮挡正在对齐的形状。
- 交互目标不应过小；操作按钮在真实手机上需易于触达。
- **错误反馈轻量：** 简短抖动/提示，不用反复弹阻断对话框。
- **成功反馈短而明确：** 合箱、音效、小粒子等可以组合，但允许玩家快速进入下一关。
- 全局音效设置必须在重启后保持。
- **动画不参与规则计算。** 先完成状态提交，再播放表现层动画；快速连续操作不会导致状态错乱。

## 7. 关卡设计要求（GDD 输入约束）

### 7.1 前 10 关教学节奏

以下仅是**机制与难度目标**，不是已校验的可运行关卡数据。

| 关卡 | 教学/体验目标 | 建议机制 | 设计目标时长（非实测） | V1.1 数据状态 |
| --- | --- | --- | --- | --- |
| 1 | 第一次正确拖放并获得正反馈 | 简单矩形物品 | 15～30 秒 | 未改动 |
| 2 | 发现可以重新摆放 | 小型空间规划 | 20～40 秒 | 未改动 |
| 3 | 学会 90°旋转 | 至少一个旋转需求 | 30～60 秒 | **已重设计**（C4） |
| 4 | 体验完美填满的整齐感 | 高利用率拼图 | 40～75 秒 | 未改动 |
| 5 | 处理多种不规则形状 | L/T/长条组合 | 45～90 秒 | **已降难度**（C5） |
| 6 | 识别不可放置区域 | 固定障碍格 | 60～100 秒 | 未改动 |
| 7 | 提前规划细长物品位置 | 长条形约束 | 60～120 秒 | 未改动 |
| 8 | 多区域取舍 | 障碍形成的功能分区 | 90～150 秒 | 未改动 |
| 9 | 最后几件的重新调整 | 高填充率、多方案比较 | 90～180 秒 | **已收紧**（C6） |
| 10 | 综合复习、章节完成 | 旋转 + 障碍 + 非规则形状 | 120～240 秒 | **已加难**（C7） |

> **时长列仍是策划期目标值，不是实测值。** V1.1 依据离线难度代理指标（见 GDD 第 2.4 节）调整了 4 个关卡的数据，目的是让难度**单调上升**；这**不能替代**真人试玩。第 9、10 关在代理指标上差距很小（0.50% vs 0.37%，N=3000 下均在噪声范围内），实际体感顺序需试玩确认。

### 7.2 GDD 必须交付的结构化内容

每关必须明确：`levelId`、标题、网格行列数、障碍格、物品实例列表、每件物品格形状、能否旋转、初始朝向、默认托盘顺序、引导触发条件、至少一组**具体摆放解**、难度设计意图。

**数据校验硬要求：** 每关通过自动求解器验证“所有必需物品可以不重叠地放入棋盘”。棋盘面积足够**不代表**关卡可解。若设计要求“某物品必须旋转”或“高难度”，还需额外测试这些特性，不能仅凭存在解就断言难度成立。

### 7.3 关卡体验约束

- 第 1～2 关不得出现需要猜测隐藏规则的情况。
- 第 3 关引导必须与真实支持的旋转交互一致。
- 每次只引入一项主要新概念，避免所有机制同时叠加。
- 初版手工设计并验证 10 关；不在客户端生成未经验证的随机关卡。
- 关卡通关可存在多个解；不要求唯一解。

## 8. 存档与数据原则

### 8.1 本地存档

MVP 存储：

- 已解锁的最高关卡 ID；
- 已完成关卡 ID 集合（供关卡列表展示）；
- 音效开关状态；
- 存档结构版本号。

建议用抽象化本地存储接口封装，便于在浏览器测试环境与微信小游戏运行环境之间切换。首版离线可玩，无需注册账号或云端同步。玩家清除本地数据、换设备、卸载等情形可能导致进度丢失，后续是否云存档另行决定。

### 8.2 数据采集与指标

**MVP 先定义事件字典；接入线上统计为 P1。** 调试期可在本地观察匿名、聚合的玩法事件，不默认上传个人信息。

| 事件名称 | 触发点 | 建议字段（不含个人身份信息） |
| --- | --- | --- |
| `level_start` | 进入关卡 | `levelId`, `isReplay` |
| `item_place_success` | 提交合法落位 | `levelId`, `itemType`, `isMove` |
| `item_place_invalid` | 非法松手 | `levelId`, `reason`（越界/碰撞/障碍） |
| `item_rotate` | 成功旋转 | `levelId`, `itemType` |
| `undo_used` | 点击有效撤回 | `levelId` |
| `level_restart` | 重置关卡 | `levelId` |
| `level_complete` | 成功通关 | `levelId`, `elapsedMs`, `committedMoves` |
| `level_exit` | 未通关退出 | `levelId`, `elapsedMs` |

衍生指标：各关进入人数与完成人数、关卡完成率、关卡停留时长、非法落位频次、撤回/重置率。只有接入真实统计能力后才能计算跨玩家留存；离线本地日志不等于完整用户分析系统。

### 8.3 隐私与合规

第一版不申请不必要的设备权限，不采集联系方式/精确位置/聊天内容；若未来接入广告或统计 SDK，在上线前按实际 SDK 与微信平台要求完成隐私合规核查及必要披露。

## 9. 商业化预留（不阻碍游戏体验）

- **原则：** 广告由玩家主动选择观看；基本关卡应可不看广告完成。
- **优先候选场景：** 请求智能提示时，玩家可以选择观看激励视频换取一次提示；也可以采用首次免费、后续广告的方案，具体需测试。
- **不做：** 强制插屏、强制观看广告才能解锁基础关卡、“设计无解关卡逼看广告”、无失败机制却硬塞复活按钮。
- **技术抽象：** 后续通过 `RewardedAdService` 一类接口封装平台广告；广告未加载、播放中断、用户拒绝和奖励回调异常时，界面不会卡住，也不能错误发奖。
- **发布前确认：** 微信小游戏主体资格、类目与内容审核、广告开通与结算条件、SDK 能力等，均以实际平台最新规则为准；PRD 不承诺一定能开通广告收益。

## 10. 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 核心拖拽在目标测试机上跟手，无明显卡顿；优先保证连续触摸操作稳定，量化性能预算由 TDD 与真机测试补充 |
| 适配 | 主流竖屏设备、不同分辨率及安全区；优先竖屏，不保证横屏游戏体验 |
| 离线 | 已打包资源与关卡无联网依赖，可在支持的本地环境离线进行核心游戏 |
| 稳定性 | 频繁拖放、旋转、撤回和重置不会产生非法占位或崩溃 |
| 可测试性 | 网格校验、旋转、通关判断、关卡求解器使用纯逻辑模块并配自动测试 |
| 可维护性 | 关卡数据、业务逻辑、Cocos 场景/UI 和平台能力分层；避免在 UI 脚本中硬编码关卡 |
| 无障碍 | 合法/非法预览不只使用颜色；按钮图标配文字或明确提示，避免关键反馈仅靠音效 |
| 资产 | 美术/字体/音效需有可商用授权；游戏暂定名称发布前需检查同名及商标风险 |

## 11. 关键验收用例（首版 P0）

| ID | 验收场景 | 预期结果 |
| --- | --- | --- |
| AC01 | 第一次启动游戏 | 可进入第 1 关；教程说明简短清楚 |
| AC02 | 将物品拖到合法空格 | 成功吸附、网格占位更新、物品不再显示在未放托盘 |
| AC03 | 拖动物品跨越棋盘边界后松手 | 操作取消，物品返回原有效位置或托盘 |
| AC04 | 将物品放在障碍格/其他物品上 | 明确非法预览；不能覆盖已有物品 |
| AC05 | 拖动一个已摆放物品 | 原位置不与自身碰撞；合法落位后只占新位置 |
| AC06 | 对可旋转物品旋转 4 次 | 占位形状与朝向回到初始状态（坐标归一化后等价） |
| AC07 | 对不可旋转物品操作旋转 | 状态不变，不产生错误 |
| AC08 | 旋转后的形状越界或撞障碍 | 不提交非法棋盘状态，预览/回退表现符合 UI 规范 |
| AC09 | 撤回最新一次合法放置/移动/旋转 | 棋盘与托盘恢复到该操作前状态；再次撤回按历史顺序回退 |
| AC10 | 非法拖放后点击撤回 | 不会把非法操作计入历史 |
| AC11 | 重置关卡并确认 | 物品全部恢复初始状态，障碍不变，进度不回退 |
| AC12 | 最后一件必需物品合法摆放 | **只触发一次**通关，展示反馈并解锁下一关 |
| AC13 | 重启游戏 | 已完成关卡与最高解锁关卡仍在；临时布局重新开始 |
| AC14 | 重玩已完成关卡 | 可以重玩，不影响最高解锁进度 |
| AC15 | 完成第 10 关 | 展示章节完成页，不加载不存在的下一关 |
| AC16 | 加载一关无解/非法数据 | 开发态校验明确失败，禁止悄悄作为正式关卡发布 |
| AC17 | 快速交替拖动、旋转、撤回、重置 | 不出现重复占位、悬空物品、幽灵物品或状态不同步 |
| AC18 | 关闭音效后重新启动 | 静音设置保持，游戏其他交互不受影响 |
| **AC19** | **把已放置物品拖到行李箱网格外松手** | **物品回到托盘原 `trayOrder` 位置、保留取出时朝向、释放其占用的格子；撤回可还原到取出前的位置与朝向** |
| **AC20** | **从托盘拿起物品（从未入箱）拖到网格外松手** | **物品留在托盘，不产生任何状态变化，不进入撤回栈** |
| **AC21** | **拖拽途中被系统中断（`touchCancel` / 来电 / 下拉通知）** | **恢复操作前状态，不视为取出，不进入撤回栈，不留悬空物品** |
| **AC22** | **撤回一次「取出」** | **物品回到取出前的棋盘位置与朝向（朝向不重置为初始朝向）** |
| **AC23** | **连续撤回多次，其中包含一次旋转** | **逐条回退，每次都能还原该步之前的位置与朝向；旋转步被撤回后朝向回到旋转前** |
| **AC24** | **构造「剩余空格 < 剩余物品格数」的局面** | **出现非阻断轻提示；提示期间仍可自由拖动/取出/撤回/重置，不弹窗、不判失败** |
| **AC25** | **构造「剩余空格 ≥ 剩余物品格数」但形状放不下的局面** | **不出现任何提示（只能单向断言）；玩家仍可正常操作** |

验收规则：P0 全部通过，至少在一个浏览器调试环境与一台真实手机上完成完整 1～10 关测试；微信小游戏发布前必须再做微信真机适配和资源包测试。

## 13. 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 玩法单调 | 玩家玩几关后缺少新鲜感 | 先验证 1～10 关的机制教学节奏；再考虑障碍/分区等低成本变量 |
| 关卡不可解 | 玩家卡死但不存在正确答案 | 构建时自动求解校验，GDD 附标准解 |
| 触屏手感差 | 手指遮挡、拖放不准、物品跳格 | 早期真机测试；采用稳定拖动偏移与明显网格预览 |
| 逻辑/表现不一致 | 操作过快出现幽灵物品、重复占位 | 状态原子提交、统一单一状态源、覆盖边界测试 |
| 广告变现不足 | 广告收入低于预期 | 核心体验先验证，广告作为可选 P1，避免提前假设收益 |
| 内容制作太慢 | 每关需大量美术或手工调参 | 数据驱动、少量通用形状、美术复用、离线求解辅助 |
| 平台合规不确定 | 资格/审核/广告开通受限 | 本地/Web 可玩原型先行，正式发布前核查最新平台规则 |

## 14. 已确定事项与待决策项

### 14.1 已确定（V1.1 基线）

- 微信小游戏为目标平台，Cocos Creator + TypeScript 为优先技术方向。
- 第一版无剧情、无人物动画、无服务器、无强制广告。
- 竖屏网格装箱；可拖拽、90°旋转、重新摆放、撤回、重置。
- **已放置物品拖到网格之外 = 取出回托盘（R-06b）；取出是一次可撤回的操作。**
- **撤回回滚到该操作前的完整快照，包含位置与朝向；朝向不重置为初始朝向（R-09）。**
- **「装不下」只做面积守恒的单向非阻断提示，不判失败、不做求解式提示（R-10）。**
- 不限时、不限步数、无生命/失败机制；所有必需物品合法入箱后通关。
- 10 关作为 MVP 范围；关卡配置化且必须验证可解，且难度序列需通过离线代理指标校准。
- 当前临时关内摆放状态默认不跨启动存档；已通关进度保存。

### 14.2 待 GDD/UI/TDD 阶段进一步确认
