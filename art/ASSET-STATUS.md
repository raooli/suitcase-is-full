## 3. 已交付 2 张的核对结果

| itemType | 名称 | 数据形状(行×列) | 期望画布 @2x | 实际 PNG | 判定 |

| `prop_07_A` | 长柄伞 | 5×1（竖） | 96×480 | 192×960 | ⚠️ 朝向对，**倍率超 2 倍** |

### 3.1 问题一：导出倍率不统一（两张都有）

- 规格：逻辑 `cellSize = 48px`，出图 **@2x ⇒ 单格 96 物理像素**。
- 实际：两张 PNG 的**单格都是 192px**（= @4x），面积是规格的 4 倍。
- SVG 源本身是对的（`prop_03_D_umbrella.svg` = 96×480，单格 96），**多出来的是导出时又放大了一倍**。
- **修法：PNG 按 SVG 1:1 导出即可**（SVG 96×480 → PNG 96×480）。
- 为什么必须修：63 张若都按 @4x，纹理解压内存约 **22MB**（单张平均 300×300×4B），小游戏上不可接受；@2x 约 **5.7MB**。

### 3.2 问题二：`prop_01_A` 手机朝向反了（必须重出）

- 数据：`prop_01_A` 的 `cells = [[0,0],[0,1]]` → **1 行 2 列，横向**，且 `rotatable = false`（不可旋转救不回来）。
- 实图：192×384 → 竖向 1 列 2 行。
- **结论：手机必须横着画**（可画成"横放的手机"，不是竖屏手机的比例），重出 192×96。
- 备选：改数据把 `cells` 改成 2 行 1 列 —— **不推荐**，改 `cells` 会连锁改变标准解与 big% 难度指标，整套难度校准要重跑（GDD V1.2 已裁决 MVP 不改数据）。

## 5. 出图规格速查（转交美术时直接贴这段）

```
画布    = 包围盒列数 × 96（宽） × 包围盒行数 × 96（高）
单格    = 96 物理像素（逻辑 cellSize 48px 的 @2x）
朝向    = 该 itemType 的 cells 在 rotation=0 时的朝向（不能凭物件常识决定）
格式    = PNG-24 透明底，禁止白底假透明
命名    = sprites/props/<itemType>.png，严格等于 itemType，不加语义后缀
出血    = ≤10%，且不得遮挡邻格判定提示
单图上限 = 512×512
四朝向  = 不出图，由引擎节点旋转实现（1 张而非 4 张）
```

**形状与朝向以 `npm run art:missing` 的输出为准**——它会列出每件物品的 `itemType / 名称 / 形状 / 期望画布 / 出现关卡`。
