## 微信小游戏重建 + 终版包体复核（M3 收尾）
- 用户称「微信小游戏包已手动重建」。核验发现该包**是坏的**：`build/wechatgame` 仅 8 个 `.js`、0 PNG、`resources/index.js` 605B 空壳（游戏导入后无图）。同套源 `build/web-mobile` 含 66 PNG（证明源资源正常，是 wechatgame 构建问题）。
- **根因定位（对照实验）**：用户手动重建是**增量构建，复用了 10-19 那版 `resources` bundle 的旧缓存**（早于 63 图加入），新资源未编译进 bundle。
  - 实验 A：清目录 + `packAutoAtlas=false` → 68 PNG ✅
  - 实验 B：全新目录 + `packAutoAtlas=true` → 68 PNG ✅
  - 用户那次：旧目录 + `packAutoAtlas=true` → 0 PNG ❌
  - 结论：**根因是旧构建缓存，不是 auto-atlas**；重建前必须删 `build/wechatgame` 干净目录。
- 已用无头机制（同 preview-check 的 cocosBuild：`CREATOR` + `ELECTRON_DISABLE_SANDBOX=1`、删 `ELECTRON_RUN_AS_NODE`、startScene=Boot.uuid）重跑干净 wechatgame 构建，产出正确包：`build/wechatgame/` 235 文件、68 PNG（63 道具+3UI+logo+slogan）、4 WAV。
- **终版包体复核 ✅**：精确 **2,938,813 B = 2.94MB**（十进制，对齐 G2 口径），低于 G2 线 3.5MB，**余量 548KB**。分项 cocos-js 1487KB / assets 1198KB / web-adapter 88KB / src 28KB。
- md5 核验：4 张修复版图（prop_09_D/I、prop_10_C/G）在构建产物内全部命中修复版（非旧残缺版）。
- 已把「微信构建增量吃旧缓存→必清目录」「无头构建命令」「appid 仍为游客号」写入 MEMORY.md。

## M3-5 短屏适配落地（提交 e4ae76d）✅
- 把 `core/config.ts` 里早有、但运行时没用上的 `UI_LAYOUT_BANDS` 压缩阶梯真正接进来。此前 `BoardView.availableArea()` 固定读 L0 带高、三横带中心是编译期常量，短屏（320×568→可见设计高≈692）会把格边长压到 P-04 的 44px 之下。
- **纯函数**：`core/config.ts` 加 `maxBoardOf` / `selectLayoutBand` / `resolveLayout` + `ResolvedLayout`；`selectLayoutBand` 逐档查「设计格边长 + 320px 折算」是否都 ≥ 该档 `cellMin`，前档够用不动后档；`resolveLayout` 用 `effectiveHeight=min(可见高,844)` 推导三横带中心。**删掉**写死的 `UI_BOARD/TRAY/TOOLBAR_BAND_CENTER_Y`，新增 `UI_MAX_BOARD`(6×6)。
- **运行时单例** `view/layout.ts`：`detectVisibleDesignHeight()` 优先 `view.getVisibleSizeInDesignResolution()`、退路画布比值、兜底 844；模块加载按 844 预选型，`BootController`/`GameController` onLoad 早期再按真实最大棋盘 `initLayout`（幂等）。
- **消费方**全接 `getLayout()`：BoardView（可用区/带中心/告警）、TrayView、ToolbarView、GameController（工具栏/返回按钮用 `topBandCenterY`+`margin`）、SuitcaseLid（合盖落点）；`BootController` 启动即初始化（保证早于视图 onLoad）。
- **验证**：typecheck:view 0 错、check:arch 无违规、**test 354/354**（新增 14 例）；`preview:game`(390×844) 零错误、活动布局 **L0**、L1 棋盘仍 114px 无回归；短屏 `--viewport 320x568@2` 零错误、活动布局 **L1 托盘 160→128**（可见设计高 692.25），截图三带完整无溢出。
- **教训**：`view` 里 `screen` 的 TS 类型不可靠 → 用 `(view as {...}).getVisibleSizeInDesignResolution?.()` 显式收窄 + try/catch，退路才是 `screen` 比值。
